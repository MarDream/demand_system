四、P0 级缺陷（功能可用性受阻，建议优先修复）

P0-1 · 列表搜索/筛选为「假功能」P0
迭代列表页提供名称、状态筛选框并发送参数，但后端接口 未声明接收这两个参数，服务层仅按 projectId 过滤 —— 用户搜索任何条件，返回结果都一样，误导性极强。

P0-2 · 迭代状态值三处不一致P0
新建迭代时后端写死中文 status = "未开始"（存的是枚举 label），而前端筛选下拉提交的是英文 key not_started，枚举类又是 NOT_STARTED。三套值互不匹配：即便补上后端筛选逻辑也必然查不到数据；且前端 getStatusType/getStatusLabel 各用一套映射（中文 key / 英文 key），隐患极大。

P0-3 · 删除迭代后需求引用悬空P0
delete 只做迭代的逻辑删除，不清理该迭代下所有需求的 iteration_id。删除后需求仍指向一个不存在的迭代，导致需求详情、筛选、统计出现脏数据。

P1-1 · 无迭代详情页P1
行业标配的「迭代详情」可一屏查看需求清单、状态分布、进度与成员负载。当前点击迭代无详情入口，只能靠列表行 + 弹窗。
P1-2 · 无敏捷看板P1
看板（状态列 + 泳道 + 拖拽流转）是迭代执行的灵魂。当前需求状态流转靠需求模块自身，迭代域内无任何可视化执行视图。
P1-3 · 容量规划名存实亡P1
capacity 只有一个数字字段，无需求工作量（人天/故事点）汇总、无「已排工作量 vs 容量」对比、无超载预警，排期全凭人工感觉。
P1-4 · 无排期冲突检测P1
syncIterationRequirements 直接把需求从原迭代改排到新迭代，静默覆盖，无「该需求已在 XX 迭代，确认移入？」的提示。
