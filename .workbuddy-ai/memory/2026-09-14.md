## AI 助手 NL2SQL 数据问答改造

**需求**：结合 NL2SQL 技术改造 AI 助手，使其能用自然语言整合智能回答数据库中的数据。

**背景**：改造前助手只有三条链路（通用操作导航 / 知识库 RAG / 联网搜索），
只能回答"在哪里操作""文档写了什么"，无法回答"库里有多少、分布如何"。

**方案**：新增后端模块 `com.demand.system.module.nl2sql`，链路为
Schema 目录 → LLM 生成查询计划(JSON) → 只读安全校验 → 数据权限/软删除过滤注入 →
只读执行 → 结构化结果先下发(dataResult SSE) → LLM 流式整合性回答。

**核心安全设计（"平面 SELECT"约束 + 服务端强制注入）**：
- 单条 SELECT、恰好一个 SELECT、禁子查询/CTE/UNION/逗号连接 → 保证所有表引用都在
  最外层 FROM/JOIN，权限注入可证明完备；
- 表白名单 + 关键字黑名单 + LIMIT 强制；关键字匹配在屏蔽字面量/注释后的"骨架文本"上做，
  且只匹配最外层（按括号层级）；
- 数据权限由服务端注入（`deleted_at=0`、非超管 `org_id IN (可见组织)`），
  原 WHERE 条件整体加括号防 OR 优先级泄漏；不信任模型自己写的过滤条件。

**新增文件**：
- 后端：`module/nl2sql/**`（config/dto/schema/support/service 共 17 个类）
- 前端：`components/assistant/AssistantDataResult.vue`

### 后续（同日晚）：回归测试 + 安全加固 + 端到端实测

**2. 修掉三个真实缺陷（写测试时暴露）**
- **反引号绕过敏感列检查**：`maskLiterals` 原先把反引号内容一并抹成空格，
  导致 `SELECT \`password\` FROM users` 能过校验、`FROM \`requirements\`` 又因表名消失而校验失败。
  改为**只屏蔽反引号定界符、保留标识符内容**。
- **敏感列整词匹配漏判**：`password_hash` 不是 `password` 的整词，能过校验；
  而模型若把它别名成 `AS hash`，结果集侧的子串过滤也会失效 → 改为**标识符子串匹配**，两侧语义一致。
- **校验顺序**：裸 `*` 检查移到表白名单之后，否则 `SELECT * FROM sys_permissions`
  报"请显式列出列"而非"表越权"。
- 另：追加 LIMIT 时改用换行分隔，避免被行尾注释吞掉。

**3. 重大发现：语义库枚举值全是错的（已修）**
- 数据库列注释过期：`requirements.priority` 注释写 `critical/high/medium/low`、
  `type` 写 `feature/bug/improvement`，**真实数据是 `P0~P3` / `BUG|REQUIREMENT_DEVELOPER|TECHNICAL_SUPPORT`**，
  `status` 是中文名（新建/待分析/待确认/开发中/…，来源 `workflow_states`，各项目工作流不同）。
- 原 `Nl2SqlSemantics` 硬编码了 `RELEASED/CLOSED`、`critical`、`feature` 等**不存在的取值**，
  会导致模型生成 `WHERE status = 'RELEASED'` 这类永远查不到数据的条件。
- **修复**：删除三个硬编码 Map，改为 `SchemaCatalogService#loadDictionary()` 运行时从
  `priorities` / `requirement_types` / `workflow_states`（含 `is_final=1` 终态）读取，
  并附 `requirements.status` 实际值兜底；提示词里**有权威取值时丢弃过期列注释**；
  `businessRules()` / few-shot 里的 `RELEASED/CLOSED` 一并改为终态中文名。
- 新增 `Nl2SqlSemanticsTest` 防回归：few-shot 示例必须自身通过安全校验、白名单不得含凭据类表、
  禁止再出现 `RELEASED/CLOSED/critical`。

**4. 端到端实测（真实大模型 + 真实库，7/7 通过）**
- 用 `assistant.chat` 绑定的真实 provider（Minimax/MiniMax-M3 @ https://minnimax.chat，
  protocol=anthropic）跑完整链路：真实提示词 → 模型 → 安全校验 → 权限注入 → 真实 MySQL → 整合性回答。
- 5 个取数问题全部生成正确 SQL 并返回正确结果；模型正确使用了字典里的
  `status NOT IN ('已验收','已取消','已拒绝')` 与真实列名 `users.real_name`。
- "帮我查一下所有用户的密码" → 模型自行判定敏感并回退（`needDatabase=false`）；
  "如何新建一个需求？" → 正确回退到操作导航。
- 权限注入实测生效：非超管可见组织 `1,10` 时，`requirements`/`users` 两张表都被注入
  `deleted_at=0` 与 `org_id IN (1,10)`，且模型原条件被整体加括号。
- 整合性回答质量达标：先给结论数字 → Markdown 表格（含算出的占比）→ 数据特征
  （集中度/瓶颈）→ 结尾如实说明"已按组织范围过滤"。

## 运行时联调实测（"启动起来并测试"，跨 00:00 至 00:30）

**1. 启动方式（复用既有结论）**

  端口 8081；日志 `logs/backend.direct.log`。
  ⚠️ 后台启动时 `rm -f 日志` 与 `java > 日志` 之间有启动延迟，
  轮询脚本可能先读到**旧日志**并误判"已启动"——要同时核对 `ls -l` 的 mtime 与 `jps`。
- 前端：5170 上原有的 Vite dev server 即可（HMR 会自动加载改动），无需重启。

**2. 浏览器级验证（新增能力，见 skill `spa-e2e-verify`）**
- 项目 `demand_frontend/node_modules` 里**已有 playwright + playwright-core**，
  Chromium 也在 `~/AppData/Local/ms-playwright`（chromium-1217/1228），
  无需下载 agent-browser，直接 `NODE_PATH=<前端node_modules> node script.cjs` 即可。

**3. 实测结论（全部通过）**
- 表格 / ECharts 柱状图 / SQL 折叠面板（含注入的 `deleted_at = 0`）/ CSV 导出
  （`各状态需求数量分布.csv`，带 BOM）/ 会话历史回放（刷新后 `data_result` 完整还原）
  / 降级文案（402 时显示可读说明而非空白）/ console 0 error。
- 三账号权限差异：超管 5 行；`hujinyan` 注入 `org_id IN (1,5,7,8,9,10,11,12,13,14,15)`；
  `zhixiaodong` 注入 `org_id IN (7..14)` → 3 行。

**4. 发现并修复的真实缺陷（重要）**
- 现象：**不传 `llmModelId` 时数据问答必定 402**，即使 `assistant.chat` 已绑好可用模型。
- 根因：`assistant.nl2sql` 出厂 `model_id = NULL`；`LlmModelResolver#resolveFirst`
  在"应用未绑定模型"时会取该类型下 `is_default = 1` 的**全局默认模型**
  （本项目 = `llm_models.id = 1`，「智谱」组，余额不足），
  而 `assistant.chat` 绑的是 `id = 21`（「Minimax」组，可用）。
  原实现先调 `resolveFirst(ASSISTANT_NL2SQL)`，拿到默认模型后就不再回退。
- 修复：新增 `Nl2SqlServiceImpl#isExplicitlyBound`，只有"应用显式绑定了该模型"
  才采纳 `resolveFirst` 结果，否则回退 `assistant.chat`，最后才退回类型默认模型。
- 验证：修复前 402 降级文案；修复后不传 `llmModelId` 直接产出完整答案，
  日志 402 计数 0；`mvn test` 91 项全绿。
- ⚠️ 配置陷阱：`llm_models` 有**两个同名 `MiniMax-M3`**（id 1 智谱 / id 21 Minimax）。
  前端模型下拉按"接入组 → 模型"两级展示，切模型必须先选对**接入组**。
