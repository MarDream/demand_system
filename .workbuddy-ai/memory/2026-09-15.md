## 修复：NL2SQL 对 JSON 数组列判空错误（"哪些工单上传了附件"）

**用户反馈**（截图）：问「哪些工单是上传了附件了的」，结果卡片标题写"已上传附件的需求列表"、
返回 5 行，但每行 `attachments` 都是 `[]`；整合性回答自己也说"5 条均未实际上传附件"。
标题与数据自相矛盾 —— 典型的过滤条件写错。

**根因**：`requirements.attachments` 是 JSON 数组列，列注释只有"附件列表"。
schema 提示词里既没说它是 JSON 数组，也没给判空口径，模型就按普通列写成
`r.attachments IS NOT NULL` —— 而空数组 `[]` 同样满足 `IS NOT NULL`，
于是把全部工单都查了出来。

**修复（三处，互补）**
1. `Nl2SqlSemantics#businessRules()` 新增两条 JSON 口径：
   判"有内容"用 `JSON_LENGTH(列) > 0`（`[]` 与 NULL 都不算），
   判"没有内容"用 `(列 IS NULL OR JSON_LENGTH(列) = 0)`，展示数量用 `JSON_LENGTH(列) AS 附件数`。
2. `Nl2SqlSemantics#fewShots()` 新增示例：
   「哪些工单上传了附件？列出编号、标题和附件数」→ 带 `JSON_LENGTH(r.attachments) > 0`。
   **few-shot 是最强杠杆**，模型会直接模仿。
3. `SchemaCatalogService#buildSchemaPrompt`：凡 `COLUMN_TYPE` 以 `json` 开头的列，
   自动追加 `[JSON 列：判"有内容"用 JSON_LENGTH(列) > 0；空数组 [] 与 NULL 都不算有内容]`。
   新增私有 `isJsonType()`。这是通用兜底，覆盖 `attachments` / `attachment_permissions` /
   `attachments_json` 等所有 JSON 列，不必逐列维护。

**回归测试**：`Nl2SqlSemanticsTest` 新增 3 项（附件类 few-shot 必须用 `JSON_LENGTH` 且 `> 0`；
业务规则必须解释 JSON 数组判空；JSON 列提示文案 + `isJsonColumnType` 类型识别）。
`mvn test` → **94 项全绿**（原 91 + 3）。
顺带把提示文案与类型判断从 `SchemaCatalogService` 的私有方法提到
`Nl2SqlSemantics#jsonColumnHint()/isJsonColumnType()`，这样不连数据库也能断言。

**踩坑记录**：这次有两处 Edit 写坏了文件——
一次把「进行中的迭代」示例的 SQL 行删掉了，一次把 `businessNote` 的 `return switch (table) {` 删掉了。
都是"想插入却误用整块替换"。再次验证：**改完必须 Read 复核上下文**，
不能只看 Edit 返回成功。

**未完成**：本机 Docker Desktop 未运行、MySQL 未监听，无法跑真实链路复验。
需要用户启动 Docker Desktop（DB 是 `scripts/docker-compose.yml` 起的容器，宿主机端口 33060）后，

## 复验完成（Docker 起来之后）

Docker Desktop 起来后，`mysql` / `redis` 等容器已 `Up (healthy)`。
注意：**Windows 上 Docker 的端口映射不一定出现在 `netstat` 里**
（`docker port mysql` 显示 `0.0.0.0:33060`，但 `netstat` 看不到），
别据此判定 DB 没起来——直接连库试最靠谱。

**数据形态（实测）**：`requirements.attachments` 为 `json`、可空、注释"附件列表"；
8 条未删除需求中 1 条 NULL、7 条 `[]`、**0 条有内容**（`IS NOT NULL` 命中 7 条）。
`file_records` 全库只有 1 行（知识库的 docx，且无 `requirement_id` 关联）——
所以 `requirements.attachments` 就是需求附件的权威字段，不是存到别处了。
**结论：确实没有任何工单上传过附件**，模型的原结论是对的，错的是过滤条件。

**复验结果（同一句问题）**
| | WHERE 片段 | 行数 |
|---|---|---|
| 修复前 | `r.attachments IS NOT NULL` | 5（每行 `[]`） |
| 修复后 | `r.attachments IS NOT NULL AND JSON_LENGTH(r.attachments) > 0` | **0** |

浏览器实测：卡片标题"已上传附件的工单"、"0 行"、空状态"没有查询到符合条件的数据"，
SQL 面板显示 `JSON_LENGTH(r.attachments) > 0`，console 0 error。
截图存档 `docs/images/nl2sql/attachments-fixed.png`。

**前端启动**：`npm run dev` 只绑 `127.0.0.1:5170`（**不是** `localhost`），
Playwright 脚本里 base URL 与 cookie domain 都要用 `127.0.0.1`，否则连不上。

**残留小瑕疵 → 已修**：整合性回答的"可能原因"会臆测一个不存在的 `requirement_attachments` 表。
根因在 `Nl2SqlPromptBuilder#buildAnswerSystemPrompt` 第 4 条"结果为空时…并建议如何调整查询条件"
——等于邀请模型自由发挥，且没有"不许引用未出现过的表"的约束。
改法：去掉"建议如何调整查询条件"；新增"只能引用已执行的 SQL 里出现过的表名与列名，
禁止臆造不存在的表"，排查建议只能针对 SQL 本身且必须措辞为"建议核对/确认"。
复验：回答变成"当前查询条件下没有任何工单上传了附件，结果为空"+"查询条件回顾"+
"基于 SQL 本身的排查建议"，不再出现具体的不存在表名。
新增 `Nl2SqlPromptBuilderTest`（4 项）守住契约（含断言旧的诱导性措辞已移除）。
`mvn test` → **98 项全绿**。

**环境坑（新增）**
- **本机有 `http_proxy`/`https_proxy=http://127.0.0.1:14109`**：
  `curl http://localhost:8081/...` 会被代理拦成 **502**，要用 `curl --noproxy '*'`。
  Python `requests` 默认对 localhost 绕过代理，所以 `ask.py` 不受影响。
- **不要把 `taskkill` 和 `java` 塞进同一条后台命令**：那样启动的 JVM 会在
  后台任务被标记 failed 后一起被回收（日志显示 Started 过，进程却没了）。
  拆成两步：先单独 taskkill，再单独后台启动。

## 顺手修掉：requirements 枚举列的过期注释

`information_schema` 里确认了两处**会误导人**的列注释：
- `requirements.type` 注释写 `类型(feature/bug/improvement等)`，实际存
  `TECHNICAL_SUPPORT` / `REQUIREMENT_DEVELOPER` / `BUG`
- `requirements.priority` 注释写 `优先级(critical/high/medium/low)`，实际存 `P0`~`P3`
- `requirements.status` 注释只写"状态"，没说是中文状态名、也没说随项目工作流而异

**改法（关键）**：注释里**不再复述取值**（复述了还会再次过期），改成**指向字典表**：
```sql
ALTER TABLE `requirements`
  MODIFY COLUMN `type`     VARCHAR(50) NOT NULL COMMENT '需求类型编码，取值见 requirement_types.code',
  MODIFY COLUMN `priority` VARCHAR(50) NOT NULL COMMENT '优先级编码，取值见 priorities.code',
  MODIFY COLUMN `status`   VARCHAR(50) NOT NULL COMMENT '需求状态名，取值见 workflow_states.name（随项目工作流而异）';
```
- 纯注释变更，不动类型/可空/默认值。改前先确认三列 collation 与表默认一致
  （都是 `utf8mb4_0900_ai_ci`），这样 `MODIFY COLUMN` 不会偷偷改字符集。
- 已同步 `database/init.sql`（第 954~956 行），保证全新库也是对的。
- **`database/migrations/` 目录当前是空的**（原迁移文件在 git 里是删除状态），
  所以没有新增迁移文件，只改了 `init.sql` + 直接 ALTER 现库。

**多实例坑**：重启后端时发现机器上已经有两个 `DemandSystemApplication`
（用户用 `start-all.bat` 起了一个，我又起了一个），我那个绑定 8081 失败
（日志 "Port 8081 was already in use"）但仍不退出，成了僵尸 JVM。

## 多维表格「数据表」分组目录树 — 效果原型

**需求**：多维表格支持按分组管理，参考目录树型结构（用户提供截图：全部实体 / 未分组 /
进销存系统(JXC) → 未分组·销售·采购 / 客户管理系统(CRM) → 跟进中·已成交）。

**确认过的范围**（AskUserQuestion）：
- 分组对象 = **编辑器左侧「数据表」侧边栏**（不是 Base 列表页）
- 层级 = **任意层级嵌套**
- 交付 = **先出效果原型，确认后再实现**

**现状盘点**（后续实现直接复用）：
- `views/bitable/index.vue` = Base 扁平卡片网格，无分组
- `views/bitable/editor.vue` 左侧 `<aside class="editor-sidebar">` 内嵌 `components/TableSidebar.vue`，
  目前是**扁平 `el-menu`**，只有 select/create/delete 三个 emit
- 后端 `bitable_bases` / `bitable_tables` **只有 `sort_order`，无分组字段/分组表**
- `bitable_views.group_config` 是「按字段分组记录」（RecordGroupVO），**与目录树分组无关**，别混
- `docs/bitable-feature-design.md` 未规划过分组管理
- 主题 token 在 `src/styles/tokens/colors.scss`（light：primary #2563EB、border #E2E8F0、
  text-primary #0F172A、surface #FFF、background #F8FAFC）

**产出**：`docs/prototypes/bitable-table-group-tree.html`（单文件、无外部依赖、可交互原型）
已实现并验证的交互：折叠/展开、点击切换范围（全部实体=平铺 / 未分组 / 分组含子孙）、
悬浮 ＋ 与 ···（新建子分组·新建数据表·重命名·删除）、搜索过滤+高亮+自动展开命中路径、
右侧表格行拖到左侧分组归组、「归组」下拉选择器、分组跨组拖拽、防环（拖到自己/子孙被拒）、
全部折叠、底部统计。截图：`docs/images/bitable-group-tree-{app,sidebar,full}.png`

**设计要点**：
- 「全部实体」「未分组」是**前端虚拟节点，不落库**；「未分组」按需显示（该层级没有未归组表时隐藏）
- 新增 `bitable_table_groups(base_id, parent_id 自关联, name, sort_order, deleted_at)`；
  `bitable_tables` 加 `group_id BIGINT NULL`
- 分组树一次返回全量（单 Base 表量级几十~几百），折叠状态前端维护
- 删除分组：子分组与数据表**上移到父级**，不级联删除

**待用户拍板**：删除非空分组的策略、分组是否跟随 Base 权限、侧边栏是否要显示数据表叶子节点。
（用户回「确认」，即按原型默认实现：删除非空分组 → 子分组与数据表上移到父级；分组跟随 Base 权限；
侧边栏分组下不显示数据表叶子节点——与截图一致。）

**验证手法**（可复用）：用 `demand_frontend/node_modules` 里的 playwright 跑 `file:///` 静态原型，
在页面里 `document.addEventListener(..., true)` 埋点打印 dragstart/dragover/drop 序列来定位 DnD 问题。

**踩坑记录**：
1. `drop` 处理器里**先把 `drag` 置 null 再调用判定函数**，导致所有投放被判非法 ——
   那次的「防环成功」是假阳性（断言只看了 toast 文案）。判定必须在清空状态**之前**做完。
2. 搜索态下分组内的「未分组」虚拟节点没有跟随关键词过滤，需 `own.some(matches)` 再渲染。
3. Playwright 定位 `.node[data-nid=x]` 会同时命中「分组节点」和「该分组下的未分组节点」，
   必须带上 `data-ntype` 消歧（strict mode violation）。
4. 断言不要只看 toast 文案/只 catch 异常给默认值，否则会掩盖"其实没生效"。

## 补回弹框拖拽（自管理窗口丢失了 el-dialog 的 draggable）

**问题**：把 `el-dialog`（带 `:draggable="!assistantFullscreen"`）换成自管理
`.assistant-window` 后，拖拽能力丢了，窗口钉死在右下角。

**实现**（复用 FAB 那套拖拽模式）：
- `windowPos: {x,y} | null` — `null` 表示沿用 CSS 默认定位（右下角）；
  一旦拖动过就固化为 `left/top` 内联样式（`windowStyle` computed，`right/bottom: auto`）。
- 抓手：normal 态 = `.assistant-panel__header`；minimized 态 = 整个 `.assistant-mini-bar`
  （热区 `__hit` 既能点也能拖）；**maximized 态直接 return**（铺满视口拖了没意义）。
- `clampWindow()` 用 `el.offsetWidth/offsetHeight` 实测尺寸约束不越界
  （三态尺寸不同，不能写死）；`watch(windowMode)` + `nextTick` 后重新 clamp
  （拖到角落再缩放会越界）。
- **点击 vs 拖拽用 3px 阈值区分**：`winHasMoved` 在每次 `mousedown` 时重置，
  `mouseup` 后紧随的 `click` 通过 `shouldIgnoreClickAfterDrag()` 判断——
  迷你条热区既是"点击还原"入口又是拖拽把手，不判断会导致拖完就误还原。
- **按钮不触发拖拽**：`onWindowDragStart` 里 `target.closest('button, .el-button, input, textarea, .el-select, .el-dropdown, .el-tooltip')`
  命中就 return；迷你条 `.assistant-mini-bar__actions` 另加 `@mousedown.stop @touchstart.stop`。
- 拖拽中加 `.is-dragging` 关掉 transition（否则位移被 0.22s 过渡拖慢、手感发粘），
  并加 `user-select: none`。光标：header `move`，迷你条/热区 `grab`→`grabbing`。
- `onBeforeUnmount` 里要一并摘掉 window 拖拽的 4 个 document 监听。

**验证**：`scripts/verify-assistant-drag.cjs`（新增）实测
normal 拖 header (496,192)→(196,42)、minimized 拖迷你条精确落到目标点 (420,520)、
按钮上拖不动窗口、拖完不误还原、纯点击仍能还原、越界拖拽被 clamp 到 (0,0)。全部通过。

**测试踩坑**：第一版断言"位移 > 300px"误判失败——实际是拖太远撞到视口边界被 clamp 了，

## 踩坑：并发 `mvn compile` + `spring-boot:run` 会写坏 target/classes

**现象**：e2e 登录突然 500，后端日志报

### 设计要点（最终实现）

- 「全部实体」「未分组」是**前端虚拟节点，不落库**；「未分组」按需渲染
  （仅当该层级确实有未归组表时出现 → 复刻截图中 CRM 无「未分组」而 JXC 有的形态）
- 只有"分组下还有子分组"时才插入嵌套的「未分组」节点，叶子分组直接把表平铺在其下一层
- 整棵树一次返回全量（单 Base 表量级几十~几百），折叠状态纯前端维护
- 删除非空分组：`reparentChildren` + `reassignTables` 上移到父级，再软删除
- 防环：`moveGroup` 拒绝 `targetParentId == id`、跨 Base 的父、以及
  `collectDescendantIds(baseId, id).contains(targetParentId)`（自己的子孙）
- 审计：`BitableAuditHelper#record(baseId, null, userId, type, json)`（`table_id` 可空，分组级审计可复用）

### 三个"静默失败"根因（最值得记）

1. **后端返回嵌套树，前端却按扁平 props 找子节点** —— 最坑的一个。
   `childGroups()` 原来是 `props.groups.filter(g => g.parentId === parentId)`，
   而接口返回的是带 `children` 的嵌套树 → 子分组**永远找不到**。
   现象极具迷惑性：DB 里 `id=5, parent_id=4, name=销售` 完全正确、
   后端日志 `status=200`、类型检查全过，就是 UI 里不显示。
   修法：加一个 `allGroups` computed 把嵌套树压平，`childGroups()` 与"展开祖先"的 watcher 都改用它。
   ```ts
   const allGroups = computed<BitableTableGroup[]>(() => {
     const out: BitableTableGroup[] = []
     const walk = (list?: BitableTableGroup[]) => {
       ;(list || []).forEach((g) => { out.push(g); walk(g.children) })
     }
     walk(props.groups)
     return out
   })
   ```
2. **折叠态集合初始为空 → `isExpanded('all')` 恒为 true**，导致每个数据表被渲染 2~3 次
   （`全部实体` + `未分组` + 分组各一份）。修法：`collapsedKeys = ref(new Set(['all']))`
   （「全部实体」默认折叠），并去掉 `allExpanded` 里的 `!!kw ||`，避免搜索时又自动展开。
3. **DnD 判定顺序**（原型阶段就踩到、这次注意规避）：`handleDrop` 必须
   **先算 `resolveDropTarget()` 拿到结论，再 `handleDragEnd()` 清空 dragging**。
   另外 `handleDragOver` 要**无条件 `event.preventDefault()`**（否则 drop 根本不触发），
   非法目标只用 `is-reject` 做视觉拒绝。

## NL2SQL 同族缺陷排查（第二轮）：含英文枚举编码的问题会随机"不取数"

### 环境先修

- **Docker Desktop 重启**把前后端全带走了（`mysql` 显示 "Up 18 seconds"），
  且 **MySQL 宿主机端口由 33060 变回 3306**（`docker ps` 已显示 `0.0.0.0:3306->3306`），
  `application-dev.yml` 源码已是 3306 —— 但 `target/classes/application-dev.yml` 还是旧的 33060，
  **必须重新 compile 才会同步资源**。已重新 compile 并起服务。
- **本机代理端口又变了**（14109 → 2908）。`curl` 用 `--noproxy '*'` 即可，
  但 **Python `urllib` 是会走代理的**（之前记忆里写的"requests 对 localhost 自动绕过"不适用于 urllib），
  表现为 `HTTP Error 502: Bad Gateway`。已在 `ask.py` 里显式
  `urllib.request.install_opener(build_opener(ProxyHandler({})))` 修掉。
- **直接用 `java -cp target/classes` 起后端曾绑到 2818 而不是 8081**（14:30 那次启动失败）。
  但**同一命令重跑就正常绑 8081**（18:16 实测），所以是**偶发、不可复现**的，不是固定行为。
  已排查并排除：`application.yml` 与 `target/classes` 完全一致且都是 8081；
  全仓库（含 `*.yml.template`、`target/classes`）**搜不到 "2818"**；
  `SERVER_PORT` / `JAVA_TOOL_OPTIONS` / `_JAVA_OPTIONS` / `SPRING_APPLICATION_JSON` 均未设置；
  classpath 里没有任何 `config/application.yml`；代码里没有 `EnvironmentPostProcessor` /
  自定义 `PropertySource`；`management.server.port: 18081` 是**残留配置**（项目根本没引 actuator）。
  → 结论：起服务时**显式钉住端口**（`-Dserver.port=8081`，与 `start-all.bat` 第 121 行的
  `--server.port=8081` 一致），并**用日志里的 `http-nio-<port>` 行确认真的绑对了**，
  不要只看 curl 通不通（通的可能不是你的进程）。
- **Bash 工具起的 JVM 会被回收**：后台 `nohup java ... &` 起的实例可能过一阵就没了
  （14:35 起的那个活到 18:0x 后消失，18:14 起的探针实例几秒就没了）。
  跑验证前**先 `jps -l` + 探活**，别假设服务还在。
  只想快速诊断启动过程时，用**前台** `timeout 50 java ... | grep -a http-nio-`，
  既不会被回收，也够看到端口绑定行。
- **JWT 有效期 2 小时**：`tok/*.tok` 隔夜/隔几小时就 401，重跑前先 `mint.py` 重签。

### 排查手法（可复用）

1. 先把 §9.5 的结论做成**语义回归扫描** `sweep.py`：8 个问题对照数据库标准答案。
   断言分两类 —— `rows`（期望行数）与 `scalar`（期望单行聚合的**值**）。
   上一版把 `COUNT(*)` 的"值"当"行数"比，产生 2 个假失败，是**脚本的期望模型错了**，不是产品 bug。
   另加两道交叉核对：① JSON 数组列只写 `IS NOT NULL` 不用 `JSON_LENGTH` 的粗筛；
   ② 回答正文里是否出现期望值（回答不能与自己的结果矛盾）。
2. 再写**路由稳定性探针** `route.py`：同一问题连问 N 次，统计几次真的走了 NL2SQL。
   这个探针才是抓到本轮缺陷的关键 —— 单次调用看起来完全正常。

## 补漏：自定义角色管理接口缺授权校验（由上一个 Bug 的修复"暴露"出来的越权）

修好 `getDeletedAt() != null` 那个恒真守卫后，`updateCustomRole` / `deleteCustomRole` /
`removeRoleMember` 三个方法**第一次真正能执行**了——而它们身上**没有任何授权校验**
（同一文件里只有 `addRoleMember` 和 `setRolePermission` 调了 `checkManagePermission`）。
也就是说：任何登录用户都能改/删任意 Base 的自定义角色、把成员踢出去。
原先那个恒真守卫等于把漏洞遮住了，所以一直没人发现。

**修复**（照抄 `addRoleMember` 的既有范式：controller 取 userId → service 校验）：
- `BitableBaseRoleService` 三个签名加 `Long userId`：
  `updateCustomRole(roleId, dto, userId)` / `deleteCustomRole(roleId, userId)` /
  `removeRoleMember(roleId, memberType, memberId, userId)`
- impl 在 `role == null` 判空之后、业务动作之前插 `authorizationService.checkManagePermission(role.getBaseId(), userId)`
  （`checkManagePermission` = `checkPermission(baseId, userId, MemberRole.ADMIN)`，即 ADMIN 及以上）
- controller 三处加 `Long userId = SecurityUtils.getCurrentUserId();` 并透传

**教训**：修掉一个"永远抛异常"的守卫时，一定要回头确认被它挡住的那段业务代码
**除此之外还缺什么**——异常掩盖了未执行的分支，而未执行的分支往往没被 review 过。

**验证**：新增 `scripts/verify-role-authz.mjs`（20 项）→ **PASS 20 / FAIL 0**。
手法：注册一个 viewer 账号并加入 Base(1)（**必须确认 403 是"角色不够"而不是"不是成员"**——
读角色列表接口本身要求 ADMIN，viewer 必然 403，但报错文案会带出已解析的当前角色，
用它断言「当前角色为 只读」来证明成员身份成立），然后断言：
viewer 对四个写接口全部 403 且角色名/成员列表**数据未被改动**；admin 同四个操作全部成功。
脚本自清理（移出 Base + 软删测试账号 `UPDATE users SET deleted_at=1,status='inactive'`）。

**踩坑**：
- `POST /auth/login` 响应**只有** `accessToken/refreshToken/expiresIn/tokenType/needOrgBind`，**不含 user**；
  要 userId 得再调 `GET /auth/me`。
- `POST /bases/{baseId}/custom-roles` 的 body **必须带 `baseId`**：DTO 上 `@NotNull`，
  `@Valid` 在 controller `dto.setBaseId(baseId)` 之前就跑了，不带就报「Base ID不能为空」。
  （前端 `handleAddRole` 传的就是 `{ baseId: props.baseId, name }`。）

## 系统角色也能直接维护成员（用户追加需求）

**需求**（截图圈出「系统角色」列表 + 成员区）：系统角色（所有者/管理员/编辑者/评论者/只读）也要能
在这个弹窗里直接加人，而不是只提示"去协作成员里维护"。

**关键发现：后端不用改，现有接口就是干这个的**（`BitableBaseMemberController` → `BitableBaseMemberServiceImpl`）：
- `POST /bases/{baseId}/members {userId, role}` 的 `addMember` 是 **upsert**：
  用户已是成员就**改角色**，否则 insert。**授予 owner 属于所有权转移**（要求操作者是 OWNER，并把其他 owner 降级）；
  已有 owner 不能被改成别的角色（抛「不能修改所有者的角色」）。
- `DELETE /bases/{baseId}/members/{userId}` 的 `removeMember` **物理删除**该行 = 失去该 Base 全部访问权限；
  **不能移除 owner**（抛「不能移除所有者」）。
- `fillMemberProfiles` 本来就遍历**所有**角色，所以系统角色成员的 `memberName`/`memberAvatar` 早就有了。

**语义要点**：`bitable_base_members` 里**一个人只有一个系统角色**，所以"往管理员里加人"本质是
**把这个人从原角色调整过去**，不是并列新增（自定义角色才是多对多，走 `bitable_base_custom_role_members`）。
前端必须把这点讲清楚，否则用户会以为能同时属于多个系统角色。

**前端改动（只动 `PermissionManageDialog.vue`）**
1. `canManageMembers` 从"仅自定义角色"放宽为 `!!selectedRole`；新增 `isSystemRole()` / `selectedSystemRoleCode`。
2. 新增 `memberRoleByUserId`：从 `roles` 里把每个用户当前系统角色汇成 `userId → {code,label}`，
   用于选人时标注「当前：X」。
3. `handleAddMember` 分支：系统角色走 `addBaseMember(baseId, {userId, role: systemRoleCode})`，
   成功提示区分"已加入"与"已从「编辑者」调整为「管理员」"；自定义角色维持 `addRoleMember`。
4. `handleRemoveMember` 分支：系统角色走 `removeBaseMember`，确认文案强调**会失去该多维表格全部访问权限**；
   自定义角色维持 `removeRoleMember`。
5. 新增 `isRemovableMember()`：**所有者成员不可移除**（后端也会拒），所以不给 `is-removable` / 不发请求。
6. 选人弹窗对系统角色追加 `.member-add-dialog__note`（琥珀色提示框）：说明"一人只有一个角色"，
   选 owner 时额外警告"会转移所有权、当前所有者降级为管理员"；候选项右侧加 `.member-option__role` 显示「当前：X」。
7. **删掉了"系统角色成员在「协作成员」中维护"的 `.perm-members__tip`**（连样式一起清掉）。

**验证**：新增 `scripts/verify-system-role-members.cjs`（19 项）→ **PASS 19 / FAIL 0**；
并把 `verify-role-member-avatar.cjs` 里"系统角色是只读"的旧断言**反过来**（现在断言有 `+`、无 tip、owner 不可移除），
28 项全过。两个脚本都自清理。
